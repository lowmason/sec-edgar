L24: # Use storage mounts in Azure Container Apps
L25: 
L26: Feedback
L27: 
L28: Summarize this article for me
L29: ## In this article
L30: 
L31: A container app has access to different types of storage. A single app can take advantage of more than one type of storage if necessary.
L32: 
L33: Note
L34: 
L35: Avoid using special characters in volume names to prevent deployment failures. For example, a volume named `credentials.json` contains a special character (`.`) which results in a deployment error.
L36: Storage type  | Description  | Persistence  | Usage example
L37: --- | --- | --- | ---
L38: cite5†Container-scoped storage | Ephemeral storage available to a running container  | Data is available until container shuts down  | Writing a local app cache.
L39: cite6†Replica-scoped storage | Ephemeral storage for sharing files between containers in the same replica  | Data is available until replica shuts down  | The main app container writing log files that a sidecar container processes.
L40: cite7†Azure Files | Permanent storage  | Data is persisted to Azure Files  | Writing files to a file share to make data accessible by other systems.
L41: Note
L42: 
L43: Azure Container Apps doesn't support mounting file shares from Azure NetApp Files or Azure Blob Storage.
L44: ## Ephemeral storage
L45: 
L46: A container app can read and write temporary data to ephemeral storage. Ephemeral storage can be scoped to a container or a replica. The total amount of container-scoped and replica-scoped storage available to each replica depends on the total number of vCPUs allocated to the replica.
L47: 
L48: vCPUs  | Total ephemeral storage
L49: --- | ---
L50: 0.25 or lower  | 1 GiB
L51: 0.5 or lower  | 2 GiB
L52: 1 or lower  | 4 GiB
L53: Over 1  | 8 GiB
L54: ### Container-scoped storage
L55: 
L56: A container can write to its own file system.
L57: 
L58: Container file system storage has the following characteristics:
L59: 
L60:   * The storage is temporary and disappears when the container shuts down or restarts.
L61:   * Only processes running in the current container can see files written to this storage.
L62: ### Replica-scoped storage
L63: 
L64: You can mount an ephemeral, temporary volume that's equivalent to cite8†EmptyDir†kubernetes.io (empty directory) in Kubernetes. This storage is scoped to a single replica. Use an `EmptyDir` volume to share data between containers in the same replica.
L65: 
L66: Replica-scoped storage has the following characteristics:
L67:   * Files persist for the lifetime of the replica.
L68:     * If a container in a replica restarts, the files in the volume remain.
L69:   * Any init or app containers in the replica can mount the same volume.
L70:   * A container can mount multiple `EmptyDir` volumes.
L71: 
L72: To configure replica-scoped storage, first define an `EmptyDir` volume in the revision. Then define a volume mount in one or more containers in the revision.

L80: #### Configuration
L81: 
L82: When you configure replica-scoped storage by using the Azure CLI, you must use a YAML definition to create or update your container app.
L83: 
L84:   1. To update an existing container app to use replica-scoped storage, export your app's specification to a YAML file named app.yaml.
L85: 
L86:     `az containerapp show -n <APP_NAME> -g <RESOURCE_GROUP_NAME> -o yaml > app.yaml
L87:     `
L88: 
L89:   2. Make the following changes to your container app specification.
L90:      * Add a `volumes` array to the `template` section of your container app definition and define a volume. If you already have a `volumes` array, add a new volume to the array.
L91:        * The `name` is an identifier for the volume.
L92:        * Use `EmptyDir` as the `storageType`.
L93:      * For each container in the template that you want to mount the volume, define a volume mount in the `volumeMounts` array of the container definition.
L94:        * The `volumeName` is the name defined in the `volumes` array.
L95:        * The `mountPath` is the path in the container to mount the volume.
L96: 
L97:     `properties:
L98:       managedEnvironmentId: /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP_NAME>/providers/Microsoft.App/managedEnvironments/<ENVIRONMENT_NAME>
L99:       configuration:
L100:         activeRevisionsMode: Single
L101:       template:
L102:         containers:
L103:         - image: <IMAGE_NAME1>
L104:           name: my-container-1
L105:           volumeMounts:
L106:           - mountPath: /myempty
L107:             volumeName: myempty
L108:         - image: <IMAGE_NAME_2>
L109:           name: my-container-2
L110:           volumeMounts:
L111:           - mountPath: /myempty
L112:             volumeName: myempty
L113:         volumes:
L114:         - name: myempty
L115:           storageType: EmptyDir
L116:     `
L117:   3. Update your container app by using the YAML file.
L118: 
L119:     `az containerapp update --name <APP_NAME> --resource-group <RESOURCE_GROUP_NAME> \
L120:         --yaml app.yaml
L121:     `
L122: 
L123: For a full example, see the cite12†YAML specification .

L209: ## Azure Files volume
L210: 
L211: You can mount a file share from cite14†Azure Files as a volume in a container.
L212: 
L213: Important
L214: Azure Container Apps supports only classic Azure file shares, which are created within a storage account (the `Microsoft.Storage/storageAccounts/fileServices/shares` resource type). Container Apps doesn't support the newer `Microsoft.FileShares` top-level resource type. If you try to mount a `Microsoft.FileShares` resource, the operation fails. To create a supported file share, see cite15†Create a classic Azure file share .
L215: 
L216: Azure Files storage has the following characteristics:
L217:   * Files written under the mount location are persisted to the file share.
L218:   * Files in the share are available via the mount location.
L219:   * Multiple containers can mount the same file share, including ones that are in another replica, revision, or container app.
L220:   * All containers that mount the share can access files written by any other container or method.
L221:   * More than one Azure Files volume can be mounted in a single container.
L222: Azure Files supports both SMB (Server Message Block) and NFS (Network File System) protocols. You can mount an Azure Files share using either protocol. The file share you define in the environment must be configured with the same protocol used by the file share in the storage account.
L223: 
L224: To enable Azure Files storage in your container, you need to set up your environment and container app as follows:
L225: In the Azure portal, open your Container App.
L226: In the left navigation pane, under Settings, select Storage mounts.
L227: 
L228: From here you can add a new mount:
L229: 
L230:   1. Choose Azure File share as the storage type.
L231:   2. Provide the required configuration (storage account, share name, access mode).
L232:   3. Save the mount.
L233:   4. Create and deploy a new revision of your container app to apply the changes.
L234:   * Create a storage definition in the Container Apps environment.
L235:   * If you're using NFS, your environment must be configured with a custom VNet and the storage account must be configured to allow access from the VNet. For more information, see cite16†NFS file shares in Azure Files .
L236:   * If you're using NFS, the storage account must not require encrypted NFS connections. Container Apps doesn't support encryption in transit for NFS file shares. If the storage account's Require Encryption in Transit for NFS setting is enabled, or if that setting isn't configured and Secure transfer required is enabled, the mount fails with an error such as `mount.nfs: access denied by server while mounting`. For more information, see cite17†Encryption in transit for NFS Azure file shares .
L237:   * If your environment is configured with a custom VNet, you must allow ports 445 and 2049 in the network security group (NSG) associated with the subnet.
L238:   * Define a volume of type `AzureFile` (SMB) or `NfsAzureFile` (NFS) in a revision.
L239:   * Define a volume mount in one or more containers in the revision.
L240:   * The Azure Files storage account used must be accessible from your container app's virtual network. For more information, see cite18†Grant access from a virtual network .

L248: ### Configuration
L249: 
L250: When you configure a container app to mount an Azure Files volume by using Azure CLI, you must use a YAML definition to create or update your container app.
L251: 
L252: For a step-by-step tutorial on mounting an SMB file share, see cite20†Create an Azure Files storage mount in Azure Container Apps .
L253: 
L254:   1. Add a storage definition to your Container Apps environment.
L255:      * cite21†SMB L256:      * cite22†NFS L257: 
L258:     `az containerapp env storage set --name my-env --resource-group my-group \
L259:         --storage-name mystorage \
L260:         --storage-type AzureFile \
L261:         --azure-file-account-name <STORAGE_ACCOUNT_NAME> \
L262:         --azure-file-account-key <STORAGE_ACCOUNT_KEY> \
L263:         --azure-file-share-name <STORAGE_SHARE_NAME> \
L264:         --access-mode ReadWrite
L265:     `
L266: Replace `<STORAGE_ACCOUNT_NAME>` and `<STORAGE_ACCOUNT_KEY>` with the name and key of your storage account. Replace `<STORAGE_SHARE_NAME>` with the name of the file share in the storage account.
L267: Valid values for `--access-mode` are `ReadWrite` and `ReadOnly`.
L268: 
L269:     `az containerapp env storage set --name my-env --resource-group my-group \
L270:         --storage-name mystorage \
L271:         --storage-type NfsAzureFile \
L272:         --server <NFS_SERVER> \
L273:         --azure-file-share-name <STORAGE_SHARE_NAME> \
L274:         --azure-file-account-name <STORAGE_ACCOUNT_NAME> \
L275:         --azure-file-account-key <STORAGE_ACCOUNT_KEY> \
L276:         --access-mode ReadWrite
L277:     `
L278: Replace `<NFS_SERVER>` with the NFS server address in the format `<STORAGE_ACCOUNT_NAME>.file.core.windows.net`. For example, if your storage account name is `mystorageaccount`, the NFS server address is `mystorageaccount.file.core.windows.net`.
L279: Replace `<STORAGE_SHARE_NAME>` with the name of the file share in the format `/<STORAGE_ACCOUNT_NAME>/<STORAGE_SHARE_NAME>`. For example, if your storage account name is `mystorageaccount` and the file share name is `myshare`, the share name is `/mystorageaccount/myshare`.
L280: 
L281: Replace `<STORAGE_ACCOUNT_NAME>` with the name of your Azure Storage account and `<STORAGE_ACCOUNT_KEY>` with the key for your Azure Storage account, which you can find in the Azure portal.
L282: Valid values for `--access-mode` are `ReadWrite` and `ReadOnly`.
L283: 
L284: Note
L285: 
L286: To mount NFS Azure Files, you must use a Container Apps environment with a custom VNet. The Storage account must be configured to allow access from the VNet.
L287: 
L288:   2. To update an existing container app to mount a file share, export your app's specification to a YAML file named app.yaml.
L289: 
L290:     `az containerapp show -n <APP_NAME> -g <RESOURCE_GROUP_NAME> -o yaml > app.yaml
L291:     `
L292:   3. Make the following changes to your container app specification.
L293:      * Add a `volumes` array to the `template` section of your container app definition and define a volume. If you already have a `volumes` array, add a new volume to the array.
L294:        * The `name` is an identifier for the volume.
L295:        * For `storageType`, use `AzureFile` for SMB, or `NfsAzureFile` for NFS. This value must match the storage type you defined in the environment.
L296:        * For `storageName`, use the name of the storage you defined in the environment.
L297:        * The `mountOptions` is a comma-separated string of mount options. For more information, see cite23†Use mountOptions settings in Azure Files .
L298:        * The `secrets` list is a list of secrets to mount in the volume. For more information, see cite24†Mounting secrets in a volume .
L299:      * For each container in the template that you want to mount Azure Files storage, define a volume mount in the `volumeMounts` array of the container definition.
L300:        * The `volumeName` is the name defined in the `volumes` array.
L301:        * The `mountPath` is the path in the container to mount the volume.
L302:        * The `subPath` is the path in the volume to mount. If you don't specify this value, the volume root is mounted. For more information, see cite25†Sub path .
L303:      * cite26†SMB L304:      * cite27†NFS L305: 
L306:     `properties:
L307:       managedEnvironmentId: /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP_NAME>/providers/Microsoft.App/managedEnvironments/<ENVIRONMENT_NAME>
L308:       configuration:
L309:       template:
L310:         containers:
L311:         - image: <IMAGE_NAME>
L312:           name: my-container
L313:           volumeMounts:
L314:           - volumeName: azure-files-volume
L315:             mountPath: /my-files
L316:             subPath: my-sub-path
L317:         volumes:
L318:         - name: azure-files-volume
L319:           storageType: AzureFile
L320:           storageName: mystorage
L321:     `
L322: 
L323:     `properties:
L324:       managedEnvironmentId: /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP_NAME>/providers/Microsoft.App/managedEnvironments/<ENVIRONMENT_NAME>
L325:       configuration:
L326:       template:
