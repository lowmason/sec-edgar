L24: # Jobs in Azure Container Apps
L25: 
L26: Feedback
L27: 
L28: Summarize this article for me
L29: 
L30: ## In this article
L31: 
L32: Azure Container Apps jobs enable you to run containerized tasks that run for a finite duration and then stop. You can use jobs to perform tasks such as data processing, machine learning, or any scenario where on-demand processing is required.
L33: 
L34: Container apps and jobs run in the same cite5†environment , allowing them to share capabilities such as networking and logging.
L35: ## Compare container apps and jobs
L36: 
L37: There are two types of compute resources in Azure Container Apps: apps and jobs.
L38: 
L39: Apps are services that run continuously. If a container in an app fails, it restarts automatically. Examples of apps include HTTP APIs, web apps, and background services that continuously process input.
L40: Jobs are tasks that start, run for a finite duration, and stop when finished. Each execution of a job typically performs a single unit of work. Job executions start manually, on a schedule, or in response to events. Examples of jobs include batch processes that run on demand and scheduled tasks.
L41: ### Example scenarios
L42: 
L43: The following table compares common scenarios for apps and jobs:
L44: Container  | Compute resource  | Notes
L45: --- | --- | ---
L46: An HTTP server that serves web content and API requests  | App  | Configure an cite6†HTTP scale rule .
L47: A process that generates financial reports nightly  | Job  | Use the cite7†Schedule job type and configure a cron expression.
L48: A continuously running service that processes messages from an Azure Service Bus queue  | App  | Configure a cite8†custom scale rule .
L49: A job that processes a single message or a small batch of messages from an Azure queue and then stops  | Job  | Use the Event job type and cite9†configure a custom scale rule to trigger job executions when there are messages in the queue.
L50: A background task that's triggered on-demand and stops when finished  | Job  | Use the Manual job type and cite10†start executions manually or programmatically by using an API.
L51: A self-hosted GitHub Actions runner or Azure Pipelines agent  | Job  | Use the Event job type and configure a cite11†GitHub Actions or cite12†Azure Pipelines scale rule.
L52: An Azure Functions app  | App  | cite13†Deploy Azure Functions to Container Apps .
L53: An event-driven app that uses the Azure WebJobs SDK  | App  | cite8†Configure a scale rule for each event source.
L54: ## Concepts
L55: 
L56: A Container Apps environment is a secure boundary around one or more container apps and jobs. Following are some key concepts:
L57:   * Job: A job defines the default configuration that's used for each job execution. The configuration includes the container image to use, the resources to allocate, and the command to run.
L58:   * Job execution: A job execution is a single run of a job that's triggered manually, on a schedule, or in response to an event.
L59:   * Job replica: A typical job execution runs one replica defined by the job's configuration. In advanced scenarios, a job execution can run multiple replicas.
L60: cite14†Image: Diagram that provides an overview of Container Apps jobs. L61: ## Permissions
L62: 
L63: To start a container app job, your user account or service principal needs the appropriate permissions. Consider the following roles:
L64: 
L65:   * Container Apps Jobs Contributor: Allows permissions to create and manage jobs.
L66:   * Container Apps Jobs Operator: Allows permissions to read, start, and stop jobs.
L67:   * Monitoring Reader (optional): Enables viewing monitoring data for jobs.
L68: Both the Container Apps Jobs Contributor and Container Apps Jobs Operator roles include the `Microsoft.App/jobs/*/action` wildcard permission. This wildcard matches `Microsoft.App/jobs/listSecrets/action`, so both roles grant permission to read the job's secret values in plain text.
L69: If neither role matches the access you want to grant, create a cite15†custom role that lists only the actions you need. For example, the following actions let a user view, start, and stop jobs without using the `Microsoft.App/jobs/*/action` wildcard. Since this rule set includes `Microsoft.App/jobs/start/action`, grant it only to identities you trust to use the job's secrets and managed identities configured to be available to its containers:
L70:   * `Microsoft.App/jobs/read`
L71:   * `Microsoft.App/jobs/start/action`
L72:   * `Microsoft.App/jobs/stop/action`
L73:   * `Microsoft.App/jobs/stop/execution/action`
L74:   * `Microsoft.App/jobs/executions/read`
L75:   * `Microsoft.App/jobs/execution/read`
L76:   * `Microsoft.App/managedEnvironments/read`
L77: 
L78: Avoid wildcard patterns such as `Microsoft.App/jobs/*/action` in a custom role definition. This wildcard grants every current and future operation that matches the pattern, including `listSecrets`.
L79: 
L80: Warning
L81: Permission to start a job can provide access to that job's secrets even when the role doesn't include the `listSecrets` action. The cite16†Jobs - Start REST API accepts an optional execution template that can override the main and init container images, commands, and environment variables. A user who holds `Microsoft.App/jobs/start/action` and knows a secret's name can reference that secret from a container of their choosing and read its value inside the container.
L82: The container can also use any managed identity cite17†configured to be available to it . Grant permission to start a job only to identities you trust to use the job's secrets and available managed identities.
L83: For more information, see cite18†Permissions for managing secrets and cite19†Azure role-based access control .
L84: ## Job trigger types
L85: 
L86: A job's trigger type determines how the job is started. The following trigger types are available:
L87: 
L88:   * Manual: Manual jobs are triggered on demand.
L89:   * Schedule: Scheduled jobs are triggered at specific times and can run repeatedly.
L90:   * Event: Event-driven jobs are triggered by events, such as a message arriving in a queue.
L91: ### Manual jobs
L92: 
L93: Manual jobs are triggered on demand via the Azure CLI, the Azure portal, or a request to the Azure Resource Manager API.
L94: 
L95: Examples of manual jobs include:
L96: 
L97:   * A one-time processing task like migrating data from one system to another.
L98:   * An e-commerce site running as a container app starts a job execution to process inventory when an order is placed.
L99:

L163: ### Scheduled jobs
L164: 
L165: To create a scheduled job, use the job type `Schedule`.
L166: 
L167: Container Apps jobs use cron expressions to define schedules. They support the standard cite24†cron†en.wikipedia.org expression format with five fields for minute, hour, day of the month, month, and day of the week. Here are some examples of cron expressions:
L168: Expression  | Description
L169: --- | ---
L170: `*/5 * * * *`  | Runs every 5 minutes.
L171: `0 */2 * * *`  | Runs every two hours.
L172: `0 0 * * *`  | Runs every day at midnight.
L173: `0 0 * * 0`  | Runs every Sunday at midnight.
L174: `0 0 1 * *`  | Runs on the first day of every month at midnight.
L175: 
L176: Cron expressions in scheduled jobs are evaluated in Coordinated Universal Time (UTC).

L240: ### Event-driven jobs
L241: 
L242: Events from supported cite8†custom scalers trigger event-driven jobs. Examples of event-driven jobs include:
L243: 
L244:   * A job that runs when a new message is added to a queue like Azure Service Bus, Kafka, or RabbitMQ.
L245:   * A self-hosted cite11†GitHub Actions runner or cite12†Azure DevOps agent that runs when a new job is queued in a workflow or pipeline.
L246: Container apps and event-driven jobs use cite28†KEDA†keda.sh scalers. They both evaluate scaling rules on a polling interval to measure the volume of events for an event source, but the way they use the results is different.
L247: 
L248: In an app, each replica continuously processes events, and a scaling rule determines the number of replicas to run to meet demand. In event-driven jobs, each job execution typically processes a single event, and a scaling rule determines the number of job executions to run.
L249: Use jobs when each event requires a new instance of the container with dedicated resources or needs to run for a long time. Event-driven jobs are conceptually similar to cite29†KEDA scaling jobs†keda.sh .
L250: 
L251: To create an event-driven job, use the job type `Event`.
L252: 
L253:   * cite30†Azure CLI L254:   * cite31†Azure Resource Manager L255:   * cite32†Azure portal L256: To create an event-driven job by using the Azure CLI, use the `az containerapp job create` command. The following example creates an event-driven job named `my-job` in a resource group named `my-resource-group` and a Container Apps environment named `my-environment`:
L257: 
L258:     `az containerapp job create \
L259:         --name "my-job" --resource-group "my-resource-group"  --environment "my-environment" \
L260:         --trigger-type "Event" \
L261:         --replica-timeout 1800 \
L262:         --image "docker.io/myuser/my-event-driven-job:latest" \
L263:         --cpu "0.25" --memory "0.5Gi" \
L264:         --min-executions "0" \
L265:         --max-executions "10" \
L266:         --scale-rule-name "queue" \
L267:         --scale-rule-type "azure-queue" \
L268:         --scale-rule-metadata "accountName=mystorage" "queueName=myqueue" "queueLength=1" \
L269:         --scale-rule-auth "connection=connection-string-secret" \
L270:         --secrets "connection-string-secret=<QUEUE_CONNECTION_STRING>"
L271:     `
L272: The example configures an Azure Storage queue scale rule.

L335: ## Start a job execution on demand
L336: 
L337: For any job type, you can start a job execution on demand.
L338: 
L339:   * cite33†Azure CLI L340:   * cite34†Azure Resource Manager L341:   * cite35†Azure portal L342: 
L343: To start a job execution by using the Azure CLI, use the `az containerapp job start` command. The following example starts an execution of a job named `my-job` in a resource group named `my-resource-group`:
L344: 
L345:     `az containerapp job start --name "my-job" --resource-group "my-resource-group"
L346:     `
L347: To start a job execution by using the Azure Resource Manager REST API, make a `POST` request to the job's `start` operation.
L348: 
L349: The following example starts an execution of a job named `my-job` in a resource group named `my-resource-group`:
L350: 
L351:     `POST https://management.azure.com/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/my-resource-group/providers/Microsoft.App/jobs/my-job/start?api-version=2023-05-01
L352:     Authorization: Bearer <TOKEN>
L353:     `
L354: 
L355: Replace `<SUBSCRIPTION_ID>` with your subscription ID.
L356: To authenticate the request, replace `<TOKEN>` in the `Authorization` header with a valid bearer token. The identity used to generate the token must have the `Microsoft.App/jobs/start/action` permission on the Container Apps job resource. The Container Apps Jobs Operator and Container Apps Jobs Contributor built-in roles include this permission. For more information, see the cite16†Jobs - Start REST API .
L357: 
L358: To start a job execution in the Azure portal, select Run now on the job's overview page.
L359: When you start a job execution, you can choose to override the job's configuration. For example, you can override an environment variable or the startup command to run the same job with different inputs. The overridden configuration is only used for the current execution and doesn't change the job's configuration.
L360: 
L361: When you override a configuration, the job's entire template configuration is replaced with the new configuration. Ensure that the new configuration includes all required settings.
L362: 
L363: Warning
L364: An identity that can start a job can use an execution template to reference job secrets whose names it knows and use managed identities configured to be available to the container. For more information, see cite36†Permissions .
L365: 
L366:   * cite37†Azure CLI L367:   * cite38†Azure Resource Manager L368:   * cite39†Azure portal L369: To override the job's configuration when you start an execution, use the `az containerapp job start` command and pass a YAML file containing the template to use for the execution. The following example starts an execution of a job named `my-job` in a resource group named `my-resource-group`.
L370: Retrieve the job's current configuration with the `az containerapp job show` command, and save the template to a file named `my-job-template.yaml`:
L371: 
L372:     `az containerapp job show --name "my-job" --resource-group "my-resource-group" --query "properties.template" --output yaml > my-job-template.yaml
L373:     `
L374: 
L375: The `--query "properties.template"` option returns only the job's template configuration.
L376: Edit the `my-job-template.yaml` file to override the job's configuration. For example, to override the environment variables, modify the `env` section:
L377: 
L378:     `containers:
L379:     - name: print-hello
L380:       image: ubuntu
L381:       resources:
L382:         cpu: 1
L383:         memory: 2Gi
L384:       env:
L385:       - name: MY_NAME
L386:         value: Azure Container Apps jobs
L387:       args:
L388:       - /bin/bash
L389:       - -c
L390:       - echo "Hello, $MY_NAME!"
L391:     `
L392: Start the job using the template:
L393: 
L394:     `az containerapp job start --name "my-job" --resource-group "my-resource-group" \
L395:         --yaml my-job-template.yaml
L396:     `
L397: To override the job's configuration, include a template in the request body. The following example overrides the startup command to run a different command:
L398: 
L399:     `POST https://management.azure.com/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/my-resource-group/providers/Microsoft.App/jobs/my-job/start?api-version=2023-05-01
L400:     Content-Type: application/json
L401:     Authorization: Bearer <TOKEN>
L402: 
L403:     {
L404:         "containers": [
L405:             {
L406:                 "image": "mcr.microsoft.com/k8se/quickstart-jobs:latest",
L407:                 "name": "main",
L408:                 "resources": {
L409:                     "cpu": 0.25,
L410:                     "memory": "0.5Gi"
L411:                 },
L412:                 "command": [
L413:                     "echo",
L414:                     "Hello, Azure Container Apps jobs!"
L415:                 ]
L416:             }
L417:         ]
L418:     }
L419:     `
L420: Replace `<SUBSCRIPTION_ID>` with your subscription ID and `<TOKEN>` in the `Authorization` header with a valid bearer token. The identity used to generate the token must have the `Microsoft.App/jobs/start/action` permission on the Container Apps job resource. The Container Apps Jobs Operator and Container Apps Jobs Contributor built-in roles include this permission. For more information, see the cite16†Jobs - Start REST API .
L421: Starting a job execution with an overridden configuration isn't supported in the Azure portal.
L422: ## Get job execution history
L423: 
L424: Each Container Apps job maintains a history of recent job executions.
L425: 
L426:   * cite40†Azure CLI L427:   * cite41†Azure Resource Manager L428:   * cite42†Azure portal L429: To get the statuses of job executions by using the Azure CLI, use the `az containerapp job execution list` command. The following example returns the status of the most recent execution of a job named `my-job` in a resource group named `my-resource-group`:
L430: 
L431:     `az containerapp job execution list --name "my-job" --resource-group "my-resource-group"
L432:     `
L433: To get the status of job executions by using the Azure Resource Manager REST API, make a `GET` request to the job's `executions` operation. The following example returns the status of the most recent execution of a job named `my-job` in a resource group named `my-resource-group`:
L434: 
L435:     `GET https://management.azure.com/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/my-resource-group/providers/Microsoft.App/jobs/my-job/executions?api-version=2023-05-01
L436:     `

L438: 
L439: To authenticate the request, add an `Authorization` header that contains a valid bearer token. For more information, see cite43†Azure REST API reference .
L440: 
L441: To view the status of job executions by using the Azure portal, search for Container App Jobs in the Azure portal and select the job. In the left pane, under Monitoring, select Execution history to see the status of recent executions.
L442: The execution history for scheduled and event-based jobs is limited to the most recent 100 successful and failed job executions.
L443: 
L444: To list all executions of a job or to get detailed output from a job, query the logs provider configured for your Container Apps environment.
L445: ## Advanced job configuration
L446: 
L447: Container Apps jobs support advanced configuration options such as container settings, retries, timeouts, and parallelism.
L448: 
L449: ### Container settings
L450: 
L451: Container settings define the containers to run in each replica of a job execution. They include environment variables, secrets, and resource limits. For more information, see cite44†Containers . Running multiple containers in a single job is an advanced scenario. Most jobs run a single container.
L452: ### Job settings
L453: 
L454: The following table includes the job settings that you can configure:
L455: Setting  | Azure Resource Manager property  | CLI parameter  | Description
L456: --- | --- | --- | ---
L457: Job type  | `triggerType`  | `--trigger-type`  | The type of job (`Manual`, `Schedule`, or `Event`).
L458: Replica timeout  | `replicaTimeout`  | `--replica-timeout`  | The maximum time in seconds to wait for a replica to complete.
L459: Polling interval  | `pollingInterval`  | `--polling-interval`  | The time in seconds to wait between polling for events. The default is 30 seconds.
L460: Replica retry limit  | `replicaRetryLimit`  | `--replica-retry-limit`  | The maximum number of times to retry a failed replica. To fail a replica without retrying, set the value to `0`. The `replicaTimeout` setting takes precedence if it expires before all retries occur.
L461: Parallelism  | `parallelism`  | `--parallelism`  | The number of replicas to run per execution. For most jobs, set the value to `1`.
L462: Replica completion count  | `replicaCompletionCount`  | `--replica-completion-count`  | The number of replicas to complete successfully for the execution to succeed. Most be equal to or less than the parallelism. For most jobs, set the value to `1`.
L463: ### Long-running jobs
L464: 
L465: Note
L466: 
L467: Platform maintenance, including routine security updates and upgrades, might interrupt long-running job replicas. Set the replica retry limit to at least `1`, and design your workload for at-least-once processing so that retries can safely complete the work.
