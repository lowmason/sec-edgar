You can try changing directories.\nL24: # Jobs in Azure Container Apps\nL25: \nL26: Feedback\nL27: \nL28: Summarize this article for me\nL29: \nL30: ## In this article\nL31: \nL32: Azure Container Apps jobs enable you to run containerized tasks that run for a finite duration and then stop. You can use jobs to perform tasks such as data processing, machine learning, or any scenario where on-demand processing is required.\nL33: \nL34: Container apps and jobs run in the same cite5†environment , allowing them to share capabilities such as networking and logging.\nL35: ## Compare container apps and jobs\nL36: \nL37: There are two types of compute resources in Azure Container Apps: apps and jobs.\nL38: \nL39: Apps are services that run continuously. If a container in an app fails, it restarts automatically. Examples of apps include HTTP APIs, web apps, and background services that continuously process input.\nL40: Jobs are tasks that start, run for a finite duration, and stop when finished. Each execution of a job typically performs a single unit of work. Job executions start manually, on a schedule, or in response to events. Examples of jobs include batch processes that run on demand and scheduled tasks.\nL41: ### Example scenarios\nL42: \nL43: The following table compares common scenarios for apps and jobs:\nL44: Container  | Compute resource  | Notes\nL45: --- | --- | ---\nL46: An HTTP server that serves web content and API requests  | App  | Configure an cite6†HTTP scale rule .\nL47: A process that generates financial reports nightly  | Job  | Use the cite7†Schedule job type and configure a cron expression.\nL48: A continuously running service that processes messages from an Azure Service Bus queue  | App  | Configure a cite8†custom scale rule .\nL49: A job that processes a single message or a small batch of messages from an Azure queue and then stops  | Job  | Use the Event job type and cite9†configure a custom scale rule to trigger job executions when there are messages in the queue.\nL50: A background task that's triggered on-demand and stops when finished  | Job  | Use the Manual job type and cite10†start executions manually or programmatically by using an API.\nL51: A self-hosted GitHub Actions runner or Azure Pipelines agent  | Job  | Use the Event job type and configure a cite11†GitHub Actions or cite12†Azure Pipelines scale rule.\nL52: An Azure Functions app  | App  | cite13†Deploy Azure Functions to Container Apps .\nL53: An event-driven app that uses the Azure WebJobs SDK  | App  | cite8†Configure a scale rule for each event source.\nL54: ## Concepts\nL55: \nL56: A Container Apps environment is a secure boundary around one or more container apps and jobs. Following are some key concepts:\nL57:   * Job: A job defines the default configuration that's used for each job execution. The configuration includes the container image to use, the resources to allocate, and the command to run.\nL58:   * Job execution: A job execution is a single run of a job that's triggered manually, on a schedule, or in response to an event.\nL59:   * Job replica: A typical job execution runs one replica defined by the job's configuration. In advanced scenarios, a job execution can run multiple replicas.\nL60: cite14†Image: Diagram that provides an overview of Container Apps jobs. L61: ## Permissions\nL62: \nL63: To start a container app job, your user account or service principal needs the appropriate permissions. Consider the following roles:\nL64: \nL65:   * Container Apps Jobs Contributor: Allows permissions to create and manage jobs.\nL66:   * Container Apps Jobs Operator: Allows permissions to read, start, and stop jobs.\nL67:   * Monitoring Reader (optional): Enables viewing monitoring data for jobs.\nL68: Both the Container Apps Jobs Contributor and Container Apps Jobs Operator roles include the `Microsoft.App/jobs/*/action` wildcard permission. This wildcard matches `Microsoft.App/jobs/listSecrets/action`, so both roles grant permission to read the job's secret values in plain text.\nL69: If neither role matches the access you want to grant, create a cite15†custom role that lists only the actions you need. For example, the following actions let a user view, start, and stop jobs without using the `Microsoft.App/jobs/*/action` wildcard. Since this rule set includes `Microsoft.App/jobs/start/action`, grant it only to identities you trust to use the job's secrets and managed identities configured to be available to its containers:\nL70:   * `Microsoft.App/jobs/read`\nL71:   * `Microsoft.App/jobs/start/action`\nL72:   * `Microsoft.App/jobs/stop/action`\nL73:   * `Microsoft.App/jobs/stop/execution/action`\nL74:   * `Microsoft.App/jobs/executions/read`\nL75:   * `Microsoft.App/jobs/execution/read`\nL76:   * `Microsoft.App/managedEnvironments/read`\nL77: \nL78: Avoid wildcard patterns such as `Microsoft.App/jobs/*/action` in a custom role definition. This wildcard grants every current and future operation that matches the pattern, including `listSecrets`.\nL79: \nL80: Warning\nL81: Permission to start a job can provide access to that job's secrets even when the role doesn't include the `listSecrets` action. The cite16†Jobs - Start REST API accepts an optional execution template that can override the main and init container images, commands, and environment variables. A user who holds `Microsoft.App/jobs/start/action` and knows a secret's name can reference that secret from a container of their choosing and read its value inside the container.\nL82: The container can also use any managed identity cite17†configured to be available to it . Grant permission to start a job only to identities you trust to use the job's secrets and available managed identities.\nL83: For more information, see cite18†Permissions for managing secrets and cite19†Azure role-based access control .\nL84: ## Job trigger types\nL85: \nL86: A job's trigger type determines how the job is started. The following trigger types are available:\nL87: \nL88:   * Manual: Manual jobs are triggered on demand.\nL89:   * Schedule: Scheduled jobs are triggered at specific times and can run repeatedly.\nL90:   * Event: Event-driven jobs are triggered by events, such as a message arriving in a queue.\nL91: ### Manual jobs\nL92: \nL93: Manual jobs are triggered on demand via the Azure CLI, the Azure portal, or a request to the Azure Resource Manager API.\nL94: \nL95: Examples of manual jobs include:\nL96: \nL97:   * A one-time processing task like migrating data from one system to another.\nL98:   * An e-commerce site running as a container app starts a job execution to process inventory when an order is placed.\nL99: \nL100: To create a manual job, use the job type `Manual`.\nL101: \nL102:   * cite20†Azure CLI L103:   * cite21†Azure Resource Manager L104:   * cite22†Azure portal L105: To create a manual job by using the Azure CLI, use the `az containerapp job create` command.
