L24: # Manage data retention in a Log Analytics workspace
L25: 
L26: Feedback
L27: 
L28: Summarize this article for me
L29: ## In this article
L30: 
L31: A Log Analytics workspace retains data in two states:
L32: 
L33:   * Analytics retention: In this state, data is available for monitoring, troubleshooting, and near-real-time analytics.
L34:   * Long-term retention: In this low-cost state, Analytics and Basic data is available through cite5†search jobs . Auxiliary data remains queryable throughout its total retention period.
L35: 
L36: This article explains how Log Analytics workspaces retain data and how to manage the data retention of tables in your workspace.
L37: ## Analytics, long-term, and total retention
L38: 
L39: By default, all tables in a Log Analytics workspace retain data for 30 days, except for cite6†log tables with 90-day default retention . Tables with the Analytics plan make your data available for real-time queries during this Analytics retention period. All table plans can retrieve the stored data through queries or search jobs, and the data is available for visualizations, alerts, and other features and services, based on the table plan.
L40: Extend the analytics retention period of tables with the Analytics plan up to two years. Basic plan tables have a fixed period of 30 days for queries while Auxiliary plan tables can be queried for the total retention period. Both Basic and Auxiliary tables have additional considerations however. For more information, see cite7†Query data in Basic and Auxiliary tables .
L41: 
L42: Note
L43: You can reduce the analytics retention period of Analytics tables to as little as four days using the API or CLI. However, since 31 days of analytics retention are included in the ingestion price, lowering the retention period below 31 days doesn't reduce costs.
L44: To retain data in the same table beyond the default retention period, extend the table's total retention to up to 12 years. Analytics data remains in the table after Analytics retention for the remainder of the configured total retention period. Run a search job to retrieve Analytics data after Analytics retention or Basic data older than 30 days when the query doesn't include an Auxiliary table. Auxiliary data remains queryable throughout its total retention period.
L45: ## How retention modifications work
L46: 
L47: When you shorten a table's total retention, Azure Monitor Logs waits 30 days before removing the data, so you can revert the change and avoid data loss if you made an error in configuration.
L48: 
L49: When you increase total retention, the new retention period applies to all data that was already ingested into the table and wasn't yet removed.
L50: 
L51: When you change the long-term retention settings of a table with existing data, the change takes effect immediately.
L52: 
L53: Example:
L54:   * You have an existing Analytics table with 180 days of analytics retention and no long-term retention.
L55:   * You change the analytics retention to 90 days without changing the total retention period of 180 days.
L56:   * Azure Monitor automatically treats the remaining 90 days of total retention as low-cost, long-term retention, so that data that's 90-180 days old isn't lost.

L62: ## Configure the default analytics retention period of Analytics tables
L63: 
L64: The default retention period of Analytics tables in a Log Analytics workspace is 30 days. Change the default analytics period of Analytics tables up to two years by modifying the workspace-level data retention setting. Basic and Auxiliary tables only have a total retention period, which is 30 days by default.
L65: Changing the default workspace-level data retention setting automatically affects all Analytics tables to which the default setting still applies in your workspace. If you've already changed the analytics retention of a particular table, that table isn't affected when you change the workspace default data retention setting.
L66: 
L67: Important
L68: Workspaces with 30-day retention might keep data for 31 days. If you need to retain data for 30 days only to comply with a privacy policy, configure the default workspace retention to 30 days by using the API and update the `immediatePurgeDataOn30Days` workspace property to `true`. Use the cite10†Workspaces - Update API for this operation.
L69: 
L70: The following examples set the workspace's default analytics retention to 30 days. The REST example also enables immediate removal after 30 days.
L71:   * cite11†Portal L72:   * cite12†Azure CLI L73:   * cite13†Azure PowerShell L74:   * cite14†REST L75:   * cite15†Bicep L76:   * cite16†ARM template L77:

L229: ## Configure table-level retention
L230: 
L231: By default, all tables with the Analytics data plan inherit the cite21†Log Analytics workspace's default retention setting and have no long-term retention. You can increase the analytics retention period of Analytics tables to up to 730 days at an cite22†extra cost†azure.microsoft.com .
L232: 
L233: To add long-term retention to a table with any data plan, set total retention to up to 12 years (4,383 days).
L234: 
L235: Note
L236: The Azure CLI `--total-retention-time` parameter supports up to 2,556 days (seven years). For longer retention, use the Azure portal, REST API, or a version of cite23†`Update-AzOperationalInsightsTable` that supports the requested value. The PowerShell reference lists values through 4,383 days.
L237: The following examples set an Analytics table's analytics retention to 30 days and total retention to two years (730 days), leaving 700 days of long-term retention. For Basic and Auxiliary tables, set only total retention; `retentionInDays` is read-only.
L238: 
L239:   * cite24†Portal L240:   * cite25†Azure CLI L241:   * cite26†Azure PowerShell L242:   * cite27†REST L243:   * cite28†Bicep L244:   * cite29†ARM template L245: 
L246: To modify the retention setting for a table in the Azure portal:
L247: 
L248:   1. From the Log Analytics workspaces menu, select Tables.
L249: The Tables screen lists all the tables in the workspace.
L250: 
L251:   2. Select the context menu for the table you want to configure and select Manage table.
L252: 
L253:   3. Configure the analytics retention and total retention settings in the Data retention settings section of the table configuration screen.
L254: 
L255: The following Azure CLI example uses the cite30†`az monitor log-analytics workspace table update` command. It modifies a table's retention settings by using the `--retention-time` and `--total-retention-time` parameters.

L460: 
L461: Retrieve the retention settings for a table or list the settings for all tables in a workspace.
L462: 
L463:   * cite34†Portal L464:   * cite35†Azure CLI L465:   * cite36†Azure PowerShell L466:   * cite37†REST L467: 
L468: To view a table's retention settings in the Azure portal, from the Log Analytics workspaces menu, select Tables.
L469: 
L470: The Tables screen shows the analytics retention and total retention periods for all the tables in the workspace.
L471: The following Azure CLI example uses the cite38†`az monitor log-analytics workspace table show` command. It retrieves a table's retention settings.
L472: 
L473:     `# Set variables
L474:     resourceGroupName="<ResourceGroupName>"
L475:     workspaceName="<WorkspaceName>"
L476:     tableName="<TableName>"
L477: 
L478:     # Retrieve the table retention settings
L479:     az monitor log-analytics workspace table show \
L480:       --resource-group "$resourceGroupName" \
L481:       --workspace-name "$workspaceName" \
L482:       --name "$tableName"
L483:     `
L484: 
L485: Note
L486: Azure CLI commands use the Azure Resource Manager endpoint from the current CLI context, so management.azure.com doesn't need to be specified in the command syntax.
L487: The following Azure PowerShell example uses the cite39†`Get-AzOperationalInsightsTable` cmdlet. It retrieves a table's retention settings.
L488: 
L489:     `# Set variables
L490:     $resourceGroupName = "<ResourceGroupName>"
L491:     $workspaceName = "<WorkspaceName>"
L492:     $tableName = "<TableName>"
L493: 
L494:     # Define parameters for Get-AzOperationalInsightsTable
L495:     $getAzOperationalInsightsTableParams = @{
L496:         ResourceGroupName = $resourceGroupName
L497:         WorkspaceName     = $workspaceName
L498:         TableName         = $tableName
L499:     }
L500: 
L501:     # Retrieve the table retention settings
L502:     Get-AzOperationalInsightsTable @getAzOperationalInsightsTableParams
L503:     `
L504: Note
L505: 
L506: Azure PowerShell cmdlets use the Azure Resource Manager endpoint from the current Az context, so management.azure.com doesn’t need to be specified in the cmdlet syntax.
L507: The following REST example uses the cite31†`Tables - Get` REST API operation. It retrieves a table's retention settings.
L508: 
L509:     `GET https://management.azure.com/subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/Microsoft.OperationalInsights/workspaces/{workspaceName}/tables/{tableName}?api-version={apiVersion}
L510:     Authorization: Bearer {accessToken}
L511:     `
L512: The following REST example uses the cite31†`Tables - List By Workspace` REST API operation. It retrieves retention settings for all tables in the workspace.
L513: 
L514:     `GET https://management.azure.com/subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/Microsoft.OperationalInsights/workspaces/{workspaceName}/tables?api-version={apiVersion}
L515:     Authorization: Bearer {accessToken}
L516:     `
L517: ## What happens to data when you delete a table in a Log Analytics workspace?
L518: 
L519: A Log Analytics workspace can contain several cite40†types of tables . What happens when you delete the table is different for each:
L520: Table type  | Data retention  | Recommendations  | Recovery
L521: --- | --- | --- | ---
L522: Azure table  | An Azure table holds logs from an Azure resource, or solution. When you stop sending data from your resource, or solution, data remains in the workspace until the end of the retention period defined for the table, and charged accordingly.  | To reduce charges, cite41†set table-level retention to four days, which is the minimum supported period.
L523: If the table being deleted is associated with a solution that should be removed (for example, Sentinel), remove the solution after the four-day retention period has passed.  | Enable the solution. Data recovery is subjected to table retention.
L524: cite42†Custom log table (`table_CL`)  | Custom log table holds logs from cite43†logs ingestion API , or HTTP data collector API (deprecated).
L525: When you delete a table, the table name remains reserved for fifteen days. Deleting a table in Analytics or Basic plans doesn't delete data. Table retention is set to workspace retention after fifteen days where retention charges adheres to the retention in table.
L526: Deleting a table in Auxiliary plan, deletes data permanently after fifteen days.  | To minimize charges, set cite41†table-level retention to four days, and delete the table after four days when data is trimmed.  | Analytics or Basic plans: Create the table with the same name and schema. Data recovery is subjected to table retention.
L527: Auxiliary plan: Create the table with the same name and schema during the soft delete period.
