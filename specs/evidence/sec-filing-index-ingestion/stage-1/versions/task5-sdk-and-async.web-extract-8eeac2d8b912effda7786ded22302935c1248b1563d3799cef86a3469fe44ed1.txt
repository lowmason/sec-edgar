L24: # Track asynchronous Azure operations
L25: 
L26: Feedback
L27: 
L28: Summarize this article for me
L29: 
L30: ## In this article
L31: 
L32: Some Azure REST operations run asynchronously because the operation can't be completed quickly. This article describes how to track the status of asynchronous operations through values returned in the response.
L33: ## Status codes for asynchronous operations
L34: 
L35: An asynchronous operation initially returns an HTTP status code of either:
L36: 
L37:   * 201 (Created)
L38:   * 202 (Accepted)
L39: However, that status code doesn't necessarily mean the operation is asynchronous. An asynchronous operation also returns a value for `provisioningState` that indicates the operation isn't finished. The value can vary by operation but doesn't include Succeeded, Failed, or Canceled. Those three values indicate the operation finished. If no value is returned for `provisioningState`, the operation finished and succeeded.
L40: 
L41: When the operation successfully completes, it returns either:
L42:   * 200 (OK)
L43:   * 204 (No Content)
L44: 
L45: Refer to the cite5†REST API documentation to see the responses for the operation you're executing.
L46: 
L47: After getting the 201 or 202 response code, you're ready to monitor the status of the operation.
L48: ## URL to monitor status
L49: 
L50: There are two different ways to monitor the status of the asynchronous operation. You determine the correct approach by examining the header values that are returned from your original request. First, look for:
L51:   * `Azure-AsyncOperation` - URL for checking the ongoing status of the operation. If your operation returns this value, use it to track the status of the operation.
L52:   * `Retry-After` - The number of seconds to wait before checking the status of the asynchronous operation.
L53: 
L54: If `Azure-AsyncOperation` isn't one of the header values, then look for:
L55:   * `Location` - URL for determining when an operation is completed. Use this value only when `Azure-AsyncOperation` isn't returned.
L56:   * `Retry-After` - The number of seconds to wait before checking the status of the asynchronous operation.
L57: 
L58: When the `Retry-after` header isn't returned, cite6†implement your own retry logic .
L59: 
L60: Note
L61: 
L62: Your REST client must accept a minimum URL size of 4 KB for `Azure-AsyncOperation` and `Location`.
L63: ## Permission for tracking async status
L64: 
L65: To track the status of an asynchronous operation, you need sufficient permission at the resource group level. If you only have permission at the resource level, you can start the operation but you can't track its status. Resource group-level permission is required because the URL for tracking status isn't scoped to the resource.
L66: For example, to start a virtual machine, you need the Virtual Machine Contributor role for the resource group that contains the virtual machine. The URL for tracking a start request doesn't include the virtual machine in its path.
L67: 
L68:     `GET
L69:     https://management.azure.com/subscriptions/{subscription-id}/providers/Microsoft.Compute/locations/{region}/operations/{operation-id}?api-version=2019-12-01
L70:     `
L71: ## Azure-AsyncOperation request and response
L72: If you have a URL from the `Azure-AsyncOperation` header value, send a GET request to that URL. Use the value from `Retry-After` to schedule how often to check the status. You get a response object that indicates the status of the operation. A different response is returned when checking the status of the operation with the `Location` URL. For more information about the response from a location URL, see cite7†Create storage account (202 with Location and Retry-After) .
L73: The response properties can vary but always include the status of the asynchronous operation.
L74: 
L75:     `{
L76:         "status": "{status-value}"
L77:     }
L78:     `
L79: The following example shows other values that might be returned from the operation:
L80: 
L81:     `{
L82:         "id": "{resource path from GET operation}",
L83:         "name": "{operation-id}",
L84:         "status" : "Succeeded | Failed | Canceled | {resource provider values}",
L85:         "startTime": "2017-01-06T20:56:36.002812+00:00",
L86:         "endTime": "2017-01-06T20:56:56.002812+00:00",
L87:         "percentComplete": {double between 0 and 100 },
L88:         "properties": {
L89:             /* Specific resource provider values for successful operations */
L90:         },
L91:         "error" : {
L92:             "code": "{error code}",
L93:             "message": "{error description}"
L94:         }
L95:     }
L96:     `
L97: The error object is returned when the status is Failed or Canceled. All other values are optional. The response you receive might look different than the example.
L98: ## provisioningState values
L99: 
L100: Operations that create, update, or delete (PUT, PATCH, DELETE) a resource typically return a `provisioningState` value. When an operation completes, one of the following three values is returned:
L101: 
L102:   * Succeeded
L103:   * Failed
L104:   * Canceled
L105: 
L106: All other values indicate the operation is still running. The resource provider can return a customized value that indicates its state. For example, you receive Accepted when the request is received and running.
L107: ## Example requests and responses

L123:     `

L128:       "startTime": "2017-01-06T18:58:24.7596323+00:00",
